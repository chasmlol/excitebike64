# Excitebike 64 decompilation

A matching decompilation of **Excitebike 64** (Nintendo 64, Left Field Productions, 2000), **USA LodgeNet version**
(the hotel pay-per-play build).

| | |
|---|---|
| ROM | `Excitebike 64 (USA) (LodgeNet)`, big-endian `.z64`, 16 MB |
| SHA-1 | `3a043dc4c8b1351ca56c3ab9bb061bd7fa99c312` |

The ROM is not included: bring your own.

## Status

All code and data are decompiled and matching: the build reproduces the original ROM byte for byte.

- 1278 functions of C: 1234 in the game image, 44 in the boot loader. The boot loader's 16 copies of game functions
  are built from the same C.
- Hand-written asm (asm/): the two entry stubs, SN Systems' debug/exception stub, SwdExpand, the stub that
  starts the game, and the sound code the linker placed among the game's data (tunes.c's ADPCM block decoder,
  softmix.c's voice mixers and output converters, DECODER.C's ADPCM block decoders, and the decoders' tables:
  asm/game_tunes.s, asm/game_softmix.s, asm/game_decoder.s).
- Names: 1218 of the 1278 functions of C (1178 of 1234 in the game, 40 of 44 in the boot loader) and 1071 of the
  2947 data symbols are named; the rest are still `func_XXXXXXXX` / `D_XXXXXXXX`. The game's C is split into its
  original source files where the game's strings name them.
- [docs/overview.md](docs/overview.md) describes how the game works: threads and game states, the main structures
  (the rider struct field by field), each source file, the NES emulator, sound, saves, the track editor and what is
  particular to the LodgeNet build.
- libultra (2.0K `libgultra_rom`) is rebuilt from decompals/ultralib, libgcc's 64-bit division from
  src/libgcc/libgcc2.c; libultra_map.json says where every object sits.
- Initialized data: src/data (generated by tools/gen_data_c.py; mostly raw arrays).

Still taken from the ROM at build time (tools/build_all.py poisons every other byte of both code images before the
build and reports where each byte came from):

- the RSP microcode (rspboot, F3DEX2.NoN and F3DLX2.Rej xbus 2.08: text and data) in both images;
- the game's assets, the ROM header and the IPL3 boot code (everything outside the code images);
- two blobs declared `extern` in src/data: the boot loader's `sBootFontBitmap` (0x1000-byte bitmap) and
  `sBootSplashSwd` (0x1688 bytes of SWD-compressed data);
- 648 bytes of linker fill between objects (non-zero bytes no compiler or assembler produces; listed in
  build/out/restored_fill.txt after a build) and 80 bytes of segment markers.

## Toolchain

None of these are included.

- **SN Systems SN64** (`cppn64`, `cc1n64`, `asn64`; proprietary Win32 programs, obtain them from the N64 decomp
  community): GNU C 2.8.1 build for the game (the marijnvdwerf/sn64 1,0,0,2 release), GNU C 2.7.2 builds 0006 and
  0001 for the boot loader (decomp.me's `n64_sn272_0006` and `n64_sn272_0001`). platform.toml has the flags,
  functions.csv the compiler of each function.
- **KMC GCC 2.7.2** + binutils 2.6 for Linux (decompals/mips-gcc-2.7.2, decompals/mips-binutils-2.6) for libultra
  and libgcc.
- **decompals/ultralib** at commit `e24c836`: libultra sources and the headers the C includes (`<ultra64.h>`).
- **SWD32** by John Brandwood (github.com/jbrandwood/SWD32, Boost Software License): compresses the game's code
  segments exactly as the original.
- GNU binutils for MIPS (`mips-linux-gnu-as`, `ld`, `objcopy`), `make`, `rsync`, `cpp`: on Linux, or in WSL on
  Windows.
- Python 3.11+ (standard library). `rabbitizer` (`pip install rabbitizer`) only for tools/split.py,
  tools/gen_data_c.py and the listings of tools/sn64.py.

The build has been verified on Windows 11 with WSL (Ubuntu). On other hosts the Win32 tools run through Wine
(setting `WINE`), which is untested.

Tell the tools where everything is with environment variables or a `config.toml` (not tracked; copy
config.example.toml): `SN64_GCC281`, `SN64_GCC272_0006`, `SN64_GCC272_0001`, `ULTRALIB`, `KMC_GCC`, `SWD32`, and
optionally `MIPS_PREFIX`, `WINE`, `LIBULTRA_WORK`.

## How the ROM is put together

- ROM 0x0-0x1000: header and IPL3 (CIC-6102).
- ROM 0x1000-0x12200: the boot loader, uncompressed, loaded at 0x80000400. It decompresses the game with
  SwdExpand, copies the stub in asm/boot_gamecopy.s to 0x802F0000 and runs it: the stub moves the game image over
  the boot loader and jumps to 0x80000400.
- ROM 0x12200: a container tagged `BRSOHYES` holding the game image (0x80000400-0x800DC098) as four
  SWD32-compressed segments (each with its raw and packed size), then the game's resources.
- The header checksum is the CIC-6102 algorithm over ROM 0x1000-0x101000.

The build compiles and links every function and data symbol at its original address in copies of the two code
images, compresses the game image into the container with SWD32 and recomputes the checksum
(tools/build_rom.py).

## Building

```sh
python tools/extract.py baserom.z64        # build/extracted: boot.bin, game.bin, layout.json
python tools/build_libultra.py --objects   # build/libultra: ultralib and libgcc objects (bash; WSL on Windows)
python tools/build_all.py                  # build/out/excitebike64.z64, checked against the original SHA-1
```

The steps of tools/build_all.py can also run on their own, on a copy of the extracted images: build_code.py (C),
build_asm.py, build_libultra.py, build_data.py, then build_rom.py. To check edited functions quickly:
`python tools/build_code.py build/test --only render_update_screen_layout` reports the bytes that differ from the
original. `python tools/sn64.py render_update_screen_layout` lists the original function, `python tools/sn64.py
file.c` the compiled one.

## Naming

symbols.txt is the one place that says where a name is: the tools resolve every name of the C, the asm and the data
through it (and libultra's own names through libultra_map.json), never from the name itself. To rename symbols:

```sh
python tools/rename.py func_8000D2E0 game_main D_800EFD70 gGame    # OLD NEW pairs (how these two were named)
python tools/rename.py --file pairs.txt                            # one `OLD NEW` pair per line
```

replaces the names everywhere (sources, headers, asm, data, symbols.txt, functions.csv, tools, docs), the
`_<n>` second names with them (`OLD_3` becomes `NEW_3`), refuses a name that is already taken, and then
runs tools/build_all.py, which must still end with the original ROM's SHA-1. A new symbol needs a line in
symbols.txt.

Conventions: functions are snake_case, verb first, with their subsystem's prefix (`bike_update_suspension`,
`cam_smooth_to`, `nes_op_jsr`); globals are `gCamelCase` when several source files use them and `sCamelCase` when one
does (`gRiders`, `sCurScreen`). libultra's names are not reused, and C library names are avoided (GCC treats
`memset`, `strcpy` and the like as built-ins).

## Layout

```
functions.csv        every function-sized range of both images: name, image, address, size, module,
                     kind (c, copy, asm, libultra, padding), compiler profile, source, copy_of (the game function
                     a boot loader copy is built from)
include/             common.h (<ultra64.h> and basics), game.h (what the game's C includes: structs.h, functions.h,
                     variables.h), boot.h (the boot loader's declarations), data.h (types for src/data)
src/game/<module>.c  the game's C, one file per original source file, functions in address order
src/game/unnamed/    object files whose name is unknown: named after what they do (desert.c, replay.c, sched.c) or
                     after their segment and start address
src/boot/            the boot loader's C, one file per object and compiler
src/data/            initialized data of both images
src/libgcc/          libgcc's 64-bit division as KMC shipped it
asm/                 hand-written asm, each file naming its image and address range
symbols.txt          every name the C, asm and data use: image, address, kind (func or data), size
libultra_map.json    where each libultra object's sections sit, and libultra's symbol addresses
platform.toml        compiler profiles
tools/               extraction, build and analysis scripts (tools/common.py lists the settings)
docs/                overview.md: how the game works; compiler-notes.md: the compilers and how their output maps
                     back to C
```

## Notes

- The `func_XXXXXXXX` / `D_XXXXXXXX` names left are code and data not understood well enough yet, and many structs
  are still offsets and pad fields. Naming and documentation are welcome; tools/build_all.py checks that the build
  still matches.
- Each function was matched with its own declarations, and they don't always agree: a global seen as a different
  struct, a function declared with other parameters. Where a function's code depends on its own view, it uses a
  second name for the same symbol, the shared name plus `_<n>` (`gGame_3`, `nes_read_io_2`; same address,
  listed in the symbol table). Struct names ending in `_<n>` are different layouts that functions gave the same
  name. Unifying these is part of naming the game's data.
- 6 functions keep inline asm because the original holds instructions C does not produce (the `break 0x407` halts,
  a debug `break 0x400`, a library function from another compiler). A few others use empty asm statements to force a
  register allocation (docs/compiler-notes.md).
- The shipped libgcc 64-bit division has a word-order bug (KMC's big-endian build used the little-endian word
  order); src/libgcc/libgcc2.c reproduces it on purpose.
- Module names come from the source file names the game's strings contain (`main.c`, `bikenew.c`, `nesn64.c`,
  `../SFX.C`, `FILE.C`, ...), passed with the line number to the memory allocator. Each original file is one
  contiguous range of code, and the file-name strings sit in the data in the same order as the code, so where a
  range of code passes several names it is split at the first function that passes the next one (camera.c, height.c
  and sun.c; arngfx.c and tubegfx.c; RESMAN.C, DECODER.C and FONTCODE.C; ...). The libraries' upper-case names
  are spelled in lower case (src/game/resman.c).
